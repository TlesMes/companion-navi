## 0. 이 문서의 위치

- **목적:** 단일 사용자 데몬을 "서버 + 클라이언트"로 확장한다. 평가 대상은 서버 측 설계이고,

## 2. 목표 구조

### 2.1 구성 요소
클라이언트(데스크톱 데몬: 귀·입·1/2층·오프라인 버퍼) / API 서버(오케스트레이션·기억 원본·쿼터) /
Python 워커(CPU 배치: 피드 요약·사실 추출·임베딩 / GPU: TTS 추론·음색 학습, pull 방식) / 저장소(PostgreSQL+pgvector, Redis, 오브젝트 스토리지).
그림 한 장과 요청 한 턴의 시퀀스 다이어그램을 둔다.

### 2.2 방향: 서버 코어 + 엣지 음성 (2026.11.12)

**서버가 요청 조립·두뇌 호출·기억·피드·쿼터를 갖고, 클라이언트는 귀·게이트·입(TTS)을 갖는다.**

근거는 실서비스 전제 하나에서 전부 나온다:
- 일반 사용자에게 LLM 키 발급을 요구할 수 없다 → **두뇌 호출은 서버 키로, 서버를 거친다.**
- 클라이언트가 조립한 프롬프트를 중계하면 누구나 쓰는 무료 LLM 프록시가 된다 →
  **조립도 서버.** 클라이언트는 발화 텍스트와 턴 종류만 보낸다.
- 쿼터는 비용이 생기는 곳에서 집행한다 → 두뇌 호출과 같은 경계.
- 프레임 문구 수정이 클라이언트 배포 없이 반영된다(실측으로 여러 번 고친 자산이다).
- 서버 GPU 추론은 사용자 수에 비례해 늘어나는 유일한 원가다 → **TTS는 클라이언트.**

기각한 안: **얇은 서버**(조립=클라이언트 — BYOK 전제라 실서비스 불가) /
**전부 서버**(TTS 포함 — 원가와 오디오 전송 지연).

지연: 서버 조립이 더하는 건 왕복 1회다. 클라이언트도 어차피 LLM을 네트워크로 부르고
TTFT가 0.7~1.3초라 차이는 작을 것으로 본다(**미측정**).

### 2.2.1 원칙과의 관계
- 원칙 1(*"인격·기억의 연속성은 100% 데몬 소유. 벤더 종속 설계는 거부"*)이 겨냥하는 건
  **LLM 벤더**다. 자기 서버는 벤더가 아니므로 "데몬" → "우리 시스템"으로 읽는다.
- [aliveness.md](./aliveness.md) §3.4의 *"로컬 전용 저장이 곧 제품의 해자(외부 유출 0)"* 는
  **개인정보 보안 요구로 옮겨 읽는다**(사용자 판단 2026.11.12). 해자의 실체가 "유출되지
  않는다"였으므로, 서버에서는 저장 암호화·삭제 경로·접근 통제가 같은 자리를 맡는다(D19).
- 아직 손대지 않은 문장: [plan.md](./plan.md) D6 근거 *"기억 전체 = 파일 하나"*,
  [architecture.md](./architecture.md) 원칙 7 *"요청-응답 서버가 아니라 상태를 가진 데몬"*.
  이 방향이 확정 기록으로 올라갈 때 세 문서를 함께 개정한다.

### 2.3 실행 모드
단독(지금 그대로) / 연결(서버 원본) 두 모드를 같은 포트 뒤에서 가른다.
단독 모드를 유지하는 이유: 개발·시연·서버 장애 시 폴백, 그리고 원칙 1의 최소 보증.
**단독 모드는 개인용으로 남긴다**(사용자 판단 2026.11.12) — 본인 사용·개발·시연용이고
서비스 사용자에게 제공하는 기능이 아니다. 따라서 Conductor 두 벌(서버 Java / `conductor.py`)의
동등성은 **제품 보증 대상이 아니다.** 프레임 문구의 원본은 서버이고, `conductor.py`는 필요할 때
따라간다. 공유 픽스처는 이식 시점의 검증 수단으로만 쓴다.

### 2.4 클라이언트 배포
설치 파일·자동 업데이트·서명은 일반 데스크톱 앱과 같은 부담으로 받아들인다(사용자 판단
2026.11.12). 일반 앱과 다른 점은 로컬 모델 하나다 — 수 GB 가중치 내려받기와 GPU 환경 편차
(이 프로젝트의 RX 6600 XT도 GPU 추론이 안 됐다). §7 라우팅이 이 편차를 흡수한다.

## 3. 턴 경로 (반응형 대화)

- 어디까지 클라이언트인가: 웨이크워드·VAD·STT·검문①(수면 명령)은 클라이언트 고정
  (원칙 3·4 — 결정론 게이트와 깔때기는 로컬).
- 서버가 맡는 것: 요청 조립(Conductor)·기억 인출·두뇌 호출·(경로에 따라) TTS.
- 스트리밍 경계: 토큰 스트림과 오디오 청크가 WebSocket을 넘는다. 문장 순번·취소·재연결은 §8.
- 지연 예산: 구간별 목표치를 표로. 지금 있는 수치는 E2E 9.8초(Stage 12, GPT-SoVITS CPU)뿐이다.
- **턴 확정은 재생 보고를 받은 뒤다(G1).** 서버는 생성이 끝나면 어시스턴트 턴을 **임시**로 저장하고,
  클라이언트가 "몇 번째 문장까지 재생했다"를 알리면 그 지점에서 잘라 확정한다(`interrupted`).
  보고가 끝내 오지 않은 임시 턴의 처리(시간 만료 후 폐기 vs 전문 확정)는 미정.
- **입력 제한(G7):** 발화 길이 상한·분당 턴 수·일일 토큰 쿼터를 서버가 건다. 출력은 `max_tokens` 고정(§10).
- **서버에 못 닿을 때(G5):** 페르소나 번들에 든 사전 합성 안내 문구를 로컬에서 재생한다.
  침묵으로 두지 않는다(2초 침묵 금지).
- **프롬프트 배치(G6):** `[공통 규칙 + 카드] → 사실 → 최근 턴` 순서로 고정한다. 바뀌지 않는 것이
  앞에 와야 캐시 프리픽스가 유지된다.

## 4. 능동성 분리

- 경계: "언제=규칙 / 무엇=모델"을 그대로 쓴다. 1층(모드 게이트)·2층(hazard)은 클라이언트,
  3층(주제 선택+발화 생성)은 서버. 클라이언트가 "지금 말하겠다"고 요청할 때만 3층이 돈다.
- **보완할 점:** daily_cap은 서버도 집행한다(원가 통제이고 클라이언트는 신뢰 경계 밖).
  클라이언트 게이트는 안전(수면 침묵), 서버 게이트는 비용 — 목적이 다르므로 둘 다 둔다.
- `interaction_log`의 원본 위치: 발화 결말(responded/ignored)은 클라이언트만 안다 → 보고 경로 필요.
- 오프라인: 서버에 못 닿으면 3층이 없다 → **선제 발화는 침묵한다(G5).** 로컬 고정 힌트 폴백은 두지 않는다.
- **모드 상태(G4):** 게이트 판정은 클라이언트가 한다 — 오프라인에서도 수면 침묵이 동작해야 한다.
  서버는 최신 사본을 보관하고 활성권이 넘어갈 때 새 기기에 내려준다. 사본과 기기 상태가 다르면
  **조용한 쪽이 이긴다**(만료 안 된 SLEEP·DND·SNOOZE 우선) — 오버라이드 "더 잘래"가 기기 교체로
  풀리지 않는다. 하루 상한의 "오늘"은 계정에 둔 사용자 시간대로 센다.

## 5. 기억 계층

- **벡터 검색은 미룬다(2026.11.14, 사용자 판단): 사실 추출 먼저, 검색은 다른 부분을 다 구현한 뒤 고려.**
  - 사실 추출과 벡터 검색은 따로 결정할 수 있다. "한 달 전 이야기를 다시 꺼낸다"는 추출이 만들고,
    검색은 사실이 너무 많아 전부 넣을 수 없을 때의 수단이다.
  - 처음엔 **상한 N개를 그대로 주입**한다(최근·중요 순). `recall_relevant_facts(query, k)`의
    첫 구현이 이것이고, 나중에 벡터 어댑터로 갈아 끼운다.
  - 함께 미뤄지는 것: 질의 임베딩 호출 방식, 턴당 임베딩 지연, 임베딩 평문 저장 위험(§15.3),
    임베딩 모델 선택, pgvector·sqlite-vec 도입.
  - **나중 비용을 작게 유지하는 조건 셋:** ① 인터페이스에 `query` 인자를 지금부터 둔다(안 써도)
    ② 사실은 **혼자 읽어도 뜻이 통하는 문장**으로 저장한다 — 그래야 나중에 일괄 임베딩이 된다
    (파생 데이터라 워커 작업 하나로 채운다) ③ 사용자별 사실 수와 턴당 주입 토큰을 지금부터
    기록한다 — 도입 시점을 정하는 근거다.
  - 나중에 실제로 드는 비용: 벡터 컬럼·인덱스 추가(PostgreSQL 확장이라 새 인프라 없음),
    일괄 임베딩 작업, 온라인 경로의 질의 임베딩 호출. 마지막이 유일하게 턴 경로를 건드린다.
- 설계 본체는 Phase 4 문서 소관.
- **동기화: 서버가 원본이고, 클라이언트의 로컬 버퍼는 이벤트 발신함이다(R2).** 서버가 두뇌를
  부르므로 오프라인에서는 대화 턴이 생기지 않는다 — 올릴 턴이 없다. 발신함에 담기는 건
  재생 결과(G1)·선제 발화 결말·모드 변경뿐이고, 연결되면 순서대로 올린다.
  (애초 설계는 "대화 턴만 store-and-forward"였다. 클라이언트가 조립하던 때의 전제라 고쳤다.)
- 사실·임베딩은 파생물이라 서버가 재생성한다.
- 정해야 할 것: 이벤트의 멱등 키(클라이언트 생성 ID), 순서 보장, 삭제 요청 경로(G8 ④).
- **동시 활성 기기는 하나다(D20).** 턴이 한 곳에서만 생기므로 충돌 해소가 필요 없다.
- **활성권 = 활성 연결이다(2026.11.15 개정).** 서버는 계정당 **활성 연결 하나 + 대기 연결 여럿**을
  받는다. 메신저의 "같은 종류 기기는 한 대만 로그인"을 참고했고, 따로 관리하는 임대 상태가 없다.
  - **가져가는 조건:** 기기를 켜거나(접속), 대기 기기에 말을 건다(웨이크워드). 둘 다 "사용자가
    지금 그 기기 앞에 있다"는 신호다. 말을 거는 쪽은 우선순위와 무관하게 이긴다(사용자 오버라이드).
  - **밀려난 기기는 로그아웃되지 않는다.** 인증을 유지한 채 대기 연결로 내려간다. 대기 연결은
    턴도 선제 발화도 못 하고 승격 통지만 받는다. 메신저와 갈리는 지점이다 — 나비는 아무도 앞에
    없는 기기에서 혼자 도는 데몬이라, 로그아웃시키면 다시 로그인해 줄 사람이 없다.
  - **자리가 비면 서버가 고른다.** ① 사용자가 지정한 **기본 기기**(처음 등록한 기기가 기본값)
    ② 없으면 가장 최근에 활성이었던 대기 기기. 대기 기기끼리 요청을 경합시키지 않는다 —
    먼저 도착한 쪽이 이기면 우선순위가 무의미해진다.
  - **비었다고 보는 시점:** 연결이 끊긴 뒤 짧은 유예를 둔다(순간 단절로 활성권이 넘어가지 않게).
    값은 실구동으로 정한다.
  - 인계 때 `mode_state`와 하루 상한 집계는 서버 사본에서 내려온다(§4, G4).
  - 고친 경위: "나중에 켠 기기"(11.12) → "마지막으로 말을 건 기기 + 임대·하트비트"(11.14, R3) →
    지금 형태. R3가 막으려던 "노트북을 닫아도 집 PC가 조용한" 문제는 자동 승격이 풀기 때문에
    "부팅만으로는 뺏지 않는다"와 임대 시간이 필요 없어졌다.

## 6. 피드 공유

### 6.0 관심사 프로필 기반 수집 — ✅ 채택 (2026.11.14)

> **채택 범위:** 아래 구조(추출 → 프로필 → 주제 단위 수집 → 선택 → 되먹임)와
> **닫힌 주제 분류**(§6.0.1). 닫힌 분류가 이 구조를 전제하므로 함께 채택된 것으로 적는다.
> 아직 미정: 분류 목록 자체(크기·계층), 웹 소스, 민감 주제 목록, 가중치 산식의 값.

**문제:** 지금 구조는 사용자가 RSS 주소를 등록해야 재료가 생긴다. 일반 사용자는 RSS가 뭔지 모른다.
D13이 뉴스 API·검색을 기각한 근거는 *"로컬 1인용 데몬엔 과하다"* 였는데([feed.md](./feed.md) §1),
그 전제가 바뀌었다. feed.md §5도 "추출 키워드 → 검색형 RSS"를 MVP 밖으로만 미뤄 뒀다.

**제안:** 관심사는 대화에서 쌓이고, 수집은 **주제 단위로** 서버가 한다.

1. **추출** — 사실 추출과 같은 느린 경로(워커)가 대화에서 주제 라벨을 뽑는다. 지금의
   `normalize_topic_label`이 출발점이다.
2. **프로필** — `user_interest(user, topic_key, weight, last_seen)`. 가중치는 시간이 지나면 줄고
   다시 언급되면 오른다. **계산은 서버의 결정론 산식**이다(LLM은 라벨만 낸다 — aliveness §1.4).
3. **수집** — 사용자가 아니라 **주제 키마다** 한 번 수집·요약한다. 같은 주제를 가진 사용자가
   결과를 공유하므로 개인화해도 공유 캐시가 유지된다.
4. **선택** — 사용자의 프로필 가중치와 최신성으로 후보를 고른다. 주제 키 일치라 임베딩이 필요 없다.
5. **되먹임** — 선제 발화의 결말(응답/무시)이 그 주제의 가중치를 올리고 내린다.
   Phase 3 완료 기준("응답률 > 무시율")을 주제별로 볼 수 있게 된다.

**함께 정할 것:**
- **콜드 스타트:** 대화가 없으면 프로필이 비어 있다 → 가입 때 주제 몇 개를 고르게 한다
  (주소가 아니라 주제). 명시 등록(①)은 이 형태로 남는다.
- **민감 주제:** 대화에 나온 건강·우울 같은 주제로 뉴스를 찾아 먼저 말을 걸면 안 된다.
  프로필에 올리지 않는 주제 목록이 필요하다(`_is_safe` 훅이 그 자리).
- **외부로 나가는 질의:** 검색어는 주제 라벨뿐이어야 한다. 사용자 문장이 검색 엔진으로 새면 안 된다.
- **웹 소스(미정, 가격·약관 미확인):** ⓐ 주제별 RSS 카탈로그 매핑(가장 싸고 거침)
  ⓑ 검색형 RSS ⓒ 뉴스 API ⓓ LLM 벤더의 웹 검색 도구(가장 유연, 건당 과금·벤더 종속 →
  `FeedSource` 어댑터 뒤). ⓐ로 시작해 어댑터를 늘리는 순서를 권한다.
- 이 안이면 사용자가 주소를 넣지 않으므로 **G3의 RSS 쪽 위험(서버 측 요청 위조)은 사라진다.**
- 단독 모드는 지금의 config 기반 RSS를 그대로 쓴다.

### 6.0.1 비용 추정 (2026.11.14 — 전부 추정, 미측정)

가정: Haiku 4.5 입력 $1 / 출력 $5 per 1M 토큰([vendor_cost.md](./vendor_cost.md)), 사용자 1명이
하루 20왕복(월 600왕복), 발화 ~30토큰·답변 ~80토큰, 카드 ~1.6K 토큰. 토큰 크기는 어림값이라
Phase 4 기준선 측정이 이 표를 대체한다.

| 항목 | 단위 | 월 비용 | 무엇에 비례하나 |
| :-- | :-- | :-- | :-- |
| 대화 턴(지금도 드는 비용) | 턴당 입력 ~2.7K | ~$1.9 / 사용자 | 대화량 |
| 선제 발화 | 하루 상한 8회 | ≤ $0.7 / 사용자 | 상한 |
| **추출(사실 + 주제를 한 호출로)** | 20행마다 1회, 입력 ~1.5~3K | **$0.1~0.3 / 사용자** | 대화량 |
| **사실 주입** | 상한 50개 ≈ +1.5K 토큰/턴 | **+$0.9 / 사용자** | 상한 × 대화량 |
| **주제 수집·요약** | 새 글 1건 ≈ $0.0016 | **주제당 $0.15~0.5** | **서로 다른 주제 수** |
| 프로필 계산·정리·저장 | 산식 + 행 몇 개 | 무시 가능 | — |

읽는 법:
- **추출 자체는 싸다** — 대화 비용의 5~15%. 사실과 주제를 한 호출에서 줄 태그로 같이 뽑으면
  관심사 추출의 추가 비용은 0에 가깝다. 지금의 콜백 추출(12시간마다 1회)도 여기로 합친다.
- **비싼 건 둘이다.** ① 사실 주입 상한 — 200개를 전부 넣으면 턴당 비용이 3배가 된다. 상한은
  품질이 아니라 원가로 정해진다. ② 서로 다른 주제 수 — 혼자만 가진 주제는 공유가 안 돼
  사실상 사용자당 비용이 된다(주제 5개면 최악 $2.5/월로 대화 비용을 넘는다).
- **②를 묶는 방법: 닫힌 주제 분류 — ✅ 채택(2026.11.14).** 추출 프롬프트에 분류 목록(수백 개)을 주고 그 안에서
  고르게 한다. 목록에 없는 주제는 수집하지 않는다(프로필 키워드로만 남는다). 수집 비용이 사용자 수가 아니라 **분류 크기에 묶인 고정비**가 된다. 세부 관심
  ("GTA 6")은 프로필에 키워드로 따로 두고, 분류("게임") 안에서 후보를 고를 때 순위에만 쓴다.
  지금 `normalize_topic_label`이 못 막는 라벨 드리프트("커리어"/"이직")도 같이 풀린다.
- 저가 모델(Flash-Lite급)을 추출·요약에 쓰면 해당 줄은 대략 1/10이 된다.
- LLM 웹 검색 도구를 소스로 쓰면 건당 과금이 더해진다(가격 미확인).

### 6.1 공유 (6.0 채택 여부와 무관)

- RSS 수집·요약은 서버에서 사용자 간 공유한다.
- 스키마를 둘로 가른다: **공유 요약**(원문 해시 + 요약기 프롬프트 버전이 키) /
  **사용자별 후보**(관심사 매핑·`used_at`·TTL).
- 대화 콜백(`source='memory'`)은 공유 대상이 아니다 — 사용자 대화에서 나온다.
- 수집 주기: 서버 스케줄러. D13의 "tick piggyback"은 단독 모드에만 남는다.
- 성과 후보: 사용자 N명일 때 요약 LLM 호출 수(공유 전/후).

## 7. TTS 추론 배치와 라우팅

- 경로 넷: ① 사용자 PC GPU(엣지) ② 로컬 Supertonic(CPU, RTF 0.33~0.41) ③ 서버 GPU 워커 ④ 클라우드 TTS.
- 기본은 ①·②(클라이언트)다. ③·④는 폴백이고 **구현 순서의 맨 뒤**로 간다 — 가장 비싸고
  실서비스에 가장 덜 필요하다. (애초 계획은 ③ 먼저였다. §2.2 방향으로 뒤집었다.)
- 전체 구현 순서(제안): 턴 게이트웨이(조립·두뇌·쿼터) → 서버 기억 → 피드 공유 →
  학습 작업 큐 → 서버 TTS 폴백.
- 추론 워커와 학습 워커는 풀을 나눈다 — scale-to-zero는 학습엔 맞고 실시간 추론엔 콜드스타트 때문에 안 맞는다.
- **짚어 둘 것:** ②는 음색이 다르다. 폴백하면 원칙 2("같은 목소리")가 깨진다 —
  "느려도 같은 목소리"와 "빨라도 다른 목소리" 중 무엇을 기본으로 할지가 라우팅 기준(D21)의 일부다.
- 라우팅 입력: 기기 능력 보고(GPU 유무·실측 RTF), 서버 큐 깊이, 쿼터 잔량.
- 문장 단위 병렬 합성 + 순서 보장(순번 재조립 버퍼). 기준선은 현 N/N+1 겹침.

## 8. 클라이언트-서버 프로토콜

- 전송: WebSocket 1개(턴 스트림) + REST(설정·자산·작업).
- 메시지 종류, 문장 순번(`turn_id`·`seq`), 취소(barge-in → 서버 생성·합성 중단),
  메트릭 보고(TTFA·RTF·결말), 재연결(마지막 수신 seq부터 재개 vs 턴 폐기).
- **재생 보고(G1):** 클라이언트가 턴마다 "seq 몇 번까지 재생했다"를 보낸다. 서버의 턴 확정이 이걸 기다린다.
- **무드는 구조화 필드로 보낸다(G2).** 서버가 응답 텍스트에서 무드 태그를 떼어 별도 필드로 싣고,
  문장 분할은 클라이언트(TTS 옆)가 한다. 무드 키의 뜻은 페르소나 번들 버전이 정한다(§9).
- 기존 자산: 컨트롤 플레인이 이미 HTTP/WS다([control/server.py](../../navi/control/server.py)) —
  로컬 GUI용이라 인증이 없다. 재사용 범위와 분리 범위를 적는다.

## 9. 음색 학습 파이프라인

- zero-shot 기본, 파인튜닝 선택. 서버리스 GPU 온디맨드(scale-to-zero) + 쿼터.
- 작업 상태 머신: `QUEUED→CLAIMED→RUNNING→UPLOADING→DONE/FAILED`, `executor_type`으로 실행 위치 중립.
- 워커 API는 pull(claim) 방식 — 임대 만료·하트비트·재시도·멱등 업로드를 여기서 정의.
- 모델 manifest: `engine`, `engine_version`, `files`, `sha256`, `trained_by`.
- 로컬 학습은 구현하지 않는다. `executor_type`과 manifest가 그 틈이다.
- **페르소나 번들도 같은 manifest로 배포한다(G2).** 카드는 서버, 음색 가중치·레퍼런스 wav는
  클라이언트에 있어 둘이 어긋나면 조용히 틀린다. 번들에 버전을 붙이고 manifest에 카드 버전·
  무드 키 목록·언어·음색 파일을 함께 적는다. 서버 장애 안내 문구(G5)의 사전 합성 wav도 여기 든다.
  클라이언트 번들 버전이 서버 카드 버전과 다를 때의 거동(거부 vs 갱신 유도)은 미정.

## 10. 인증·쿼터·비용

- 기기 인증: 기기 토큰 vs OAuth device flow(D23).
- 쿼터: 학습 횟수·서버 GPU 초·LLM 토큰. 동시 요청에서 잔액 불일치 0건이 성과 후보 —
  차감 방식(조건부 UPDATE vs Redis 원자 연산 + 정산)을 비교한다.
- **LLM 키는 서버 것이다**(§2.2). 비용이 운영자에게 오므로 쿼터가 선택이 아니라 전제다.
  단독 모드의 `.env` 키(BYOK)는 그 모드에만 남는다. 남은 결정은 쿼터 단위와 한도(D24).
- 정서 안전(D10)은 서버에서 강제한다 — 클라이언트는 신뢰 경계 밖이다.
- **반응 턴 남용 방지(G7):** 턴 API는 페르소나 달린 범용 챗봇으로 쓰일 수 있다. 발화 길이 상한·
  분당 턴 수·일일 토큰 쿼터를 건다. 값은 미정(D24).
- **프롬프트 캐시(G6):** 서버 키가 되면 캐시가 원가의 핵심이다. 조립 순서를 고정하고(§3),
  두뇌 모델 선택(D1) 기준에 "카드가 그 모델의 캐시 최소 길이를 넘는가"를 넣는다 — 현 카드
  (~1.6K 토큰)는 Haiku 최소 길이(4096)에 못 미쳐 캐시가 걸리지 않는다. 사용자 간 캐시 적중률이 성과 후보다.
- **보안(D19, G8):** ① 음성은 PC를 떠나지 않는다 — 서버로 가는 건 텍스트뿐 ② 턴·사실 본문은
  사용자별 키로 필드 암호화 ③ 서버 로그에 대화 본문을 남기지 않는다 ④ 삭제는 턴→사실→임베딩으로
  연쇄한다 ⑤ LLM 벤더가 전 사용자의 대화를 받으므로 D1 기준에 데이터 처리 조건을 넣는다.
  미정: 키 관리 방식(보관 위치·교체), 내보내기 형식.

## 11. 서버 스택

- 후보: Spring MVC + Virtual Threads, PostgreSQL(+pgvector), Redis. WebFlux는 비교 근거만.
- 적을 것: 스트리밍(LLM SSE 중계·WS)에서 VT가 충분한 이유, Python 워커와의 경계(큐·프로토콜).
- **런타임 분담(R1 채택, 2026.11.14): Java는 온라인 경로만, 배치는 Python 워커.**
  - **Java(Spring):** 요청 조립·두뇌 스트리밍·쿼터·세션·기기 활성권·선제 발화 3층의 온라인 부분.
    Python에서 다시 쓰는 건 조립(`conductor.py`·`card.py`·`mood.py`)과 두뇌 클라이언트뿐이다.
  - **Python 워커:** 피드 수집·요약, 사실 추출, 임베딩, TTS 추론, 음색 학습. `navi/feed` 등
    기존 패키지를 그대로 쓴다. 단독 모드와 같은 코드라 배치 로직은 한 벌이다.
  - 둘 사이는 **pull 큐 하나**(§9의 claim 방식)다. 워커 종류는 CPU 배치 / GPU 추론 / GPU 학습으로
    풀을 나눈다.
  - 근거: 서버로 가는 Python은 약 1,500줄이고(조립 164 · 카드 146 · 무드 88 · 두뇌 ~330 ·
    피드 ~740 · 주제 42), 피드는 리뷰 7건으로 다듬은 코드다. 전부 Java로 옮기면 같은 결함을 다시 밟는다.
- **R1이 남긴 결정:**
  - ~~질의 임베딩 호출 방식~~ — **벡터 검색을 미루면서 함께 미뤘다(§5).** 도입할 때 정한다:
    Java가 부를 수 있어야 하고(임베딩 API vs Python 사이드카), 워커의 문서 임베딩과 같은 모델이어야 한다.
  - 워커가 쓴 LLM 토큰의 귀속 — 작업 결과에 사용량을 실어 서버가 기록한다(공유 피드는 운영 원가,
    사실 추출은 사용자 귀속).
  - 프레임 문구를 **데이터 파일**로 뺀다(제안). Java와 `conductor.py`가 같은 파일을 읽으면
    문구 수정이 한 곳에서 끝난다.
- **제안(미정):** Redis는 처음엔 뺀다. 작업 큐(`SKIP LOCKED`)와 쿼터 차감(행 잠금)은 PostgreSQL로
  되고, 병목이 측정되면 넣는다 — 그 전후 수치가 성과가 된다.

| G6 | ✅ **채택 → §3·§10.** **프롬프트 캐시 배치.** 서버 키가 되면 캐시가 원가의 핵심이다. 같은 카탈로그 카드를 쓰는 사용자끼리 캐시 프리픽스를 공유할 수 있는데, 현 카드(~1.6K 토큰)는 Haiku 최소 길이(4096)에 못 미쳐 캐시가 안 걸린다([anthropic.py](../../navi/brain/anthropic.py) 독스트링) | 순서를 `[공통 규칙 + 카드] → 사실 → 최근 턴`으로 고정하고, 벤더·모델 선택(D1) 기준에 "카드가 캐시 최소 길이를 넘는가"를 넣는다. **사용자 간 캐시 적중률**이 성과 후보가 된다 |
| G7 | ✅ **채택 → §3·§10.** **반응 턴 남용.** 텍스트를 받는 턴 API는 페르소나 달린 범용 챗봇으로 쓰일 수 있다 | 발화 길이 상한·분당 턴 수·일일 토큰 쿼터. 출력은 지금처럼 `max_tokens` 고정 |
| G8 | ✅ **채택 → §10·D19.** **보안 요구의 구체 항목**(D19가 비어 있었다) | ① **음성은 PC를 떠나지 않는다** — 서버로 가는 건 텍스트뿐. "로컬 전용 해자"를 잇는 문장으로 쓸 수 있다 ② 턴·사실 본문은 사용자별 키로 필드 암호화 ③ 서버 로그에 대화 본문 금지(지금 Conductor는 debug에 전문을 찍는다) ④ 삭제는 턴→사실→임베딩 연쇄 ⑤ **LLM 벤더가 대화를 받는다** — B6의 관할권 우려가 본인 한 명에서 전 사용자로 커지므로 D1의 기준에 데이터 처리 조건이 들어간다 |

### 15.3 알고 받아들이는 위험

- **임베딩은 암호화할 수 없다.** 검색하려면 평문 벡터여야 하고, 벡터에서 원문을 일부 추정할 수 있다. 서버가 조립하는 한 운영자가 볼 수 없는 구조(E2EE)는 불가능하다.
- **엣지 추론이면 음색 가중치가 사용자 디스크에 있다.** 추출을 막을 방법이 없다. D29에서 음성 확보 조건을 정할 때 전제로 둔다.
- **턴마다 질의 임베딩이 한 번 든다.** 두뇌 호출 앞에 붙는 지연이고 미측정이다.

## 16. 페르소나 출처 — ✅ 채택 (2026.11.14)

출처는 셋이다: **직접 작성 / 운영자 제공 / 사용자 간 공유.** G3의 페르소나 쪽을 대체한다.

> **채택 범위:** 아래 전부 — 스키마(소유자·공개 범위·버전), 버전 고정, 카드·음색 분리,
> 기억 범위(사실=사용자 단위 / 대화 턴=사용자×페르소나 단위), 공개 전 검사, 2단계 구현.
> 아직 미정: 필드별 길이 상한, 공개 검사의 기준과 방법, 목록의 정렬·검색 방식.
> **기존 코드와 달라지는 점:** 지금은 페르소나를 바꿔도 `conversation_turn`이 사용자 단위로
> 이어진다(`recall_recent_for_user`). 서버 스키마의 턴에는 페르소나 식별자가 들어간다.

- **모델:** `persona(id, owner, visibility: private | public | official, version, 카드 필드, language)`.
  처음부터 이 형태로 두면 공유는 나중에 덧붙이는 기능이 된다.
- **버전은 불변이고, 사용자는 버전을 고정한다.** 작성자가 카드를 고쳐도 쓰고 있는 사람의 나비는
  바뀌지 않는다(갱신은 사용자가 고른다). 원칙 1의 "인격의 연속성"이 공유에서 뜻하는 바다.
  가져다 고쳐 쓰는 건 복제(fork)다.
- **목소리는 카드와 분리한다.** 공유되는 건 카드(텍스트)와 "운영자 제공 음색 중 무엇을 쓸지"까지.
  개인이 만든 음색(레퍼런스·가중치)은 기본적으로 공유 대상이 아니다. 지금의 "페르소나 = 카드 +
  음색 + 톤 번들"이 **카드(공유 가능) + 음색 바인딩(사용자별)** 로 갈린다(G2의 manifest가 이 둘을 묶는다).
- **기억의 범위(공백):** 지금은 페르소나를 바꿔도 대화 기록이 사용자 단위로 이어진다.
  제안: **사실은 사용자 단위, 대화 턴은 사용자×페르소나 단위.** 다른 캐릭터가 남의 대화를
  "기억"하면 어색하지만, 사용자에 대한 사실은 누가 알아도 자연스럽다.
- **공개 전 검사:** 공개 카드는 다른 사람의 시스템 프롬프트가 된다. 나비는 도구·링크가 없어
  빼돌릴 통로는 없지만, 사용자를 조종하는 문구는 가능하다 → 공개 시 자동 검사 + 신고·내림.
- **원가:** 공식·인기 공개 카드는 사용자 간 프롬프트 캐시를 공유한다(G6). 비공개 카드는 못 한다.
- **단계:** ① 운영자 제공 + 직접 작성(비공개) ② 공개·복제·버전 고정·목록(검색·인기순).
  ②의 인기순 집계가 Redis를 넣을 첫 실수요가 될 수 있다.

## 1. 목표와 범위

- **목표:** "한 달 전 이야기를 다시 꺼낸다." 최근 대화 창을 넓히는 대신, 대화에서 **사실을 뽑아**
  따로 저장하고 매 턴 주입한다.
- **범위 밖(2026.11.14 결정):** 벡터 검색·임베딩·sqlite-vec. 사실이 너무 많아 전부 넣을 수 없게
  됐을 때의 수단이라 나중에 붙인다(service.md §5). 지금은 **상한 N개를 그대로 주입**한다.
- **나중 비용을 작게 두는 조건 셋** (service.md §5와 같다):
  1. 인출 인터페이스에 `query` 인자를 지금부터 둔다(안 써도).
  2. 사실은 **혼자 읽어도 뜻이 통하는 문장**으로 저장한다 — 나중에 일괄 임베딩이 된다.
  3. 사용자별 사실 수와 턴당 주입 토큰을 지금부터 기록한다 — 검색 도입 시점의 근거다.

## 2. 지금 코드의 사실 (대조 결과)

- `recent_turns: 20`은 20**턴**이 아니라 20**행**이다 — 사용자·나비 발화가 각각 한 행이라 약 10왕복.
  ([conductor.py](../../navi/conductor.py) `recall_recent_for_user(user_id, config.recent_turns)`)
- `MemoryStore`는 구체 클래스 하나에 턴·친밀도·모드·`interaction_log`·`topic_candidate`·
  `feed_meta`·`setting`·`usage_log`가 섞여 있다([store.py](../../navi/memory/store.py)).
- `append_turn`은 `turn_id`를 돌려주지 않고 `ts` 인자도 없다. architecture.md §4.5의 계약
  (`append_turn(session_id, role, text, ts)`)과 다르다.
- 스키마 마이그레이션 경로가 없다(`executescript` + `IF NOT EXISTS`). 새 테이블 추가는 되지만
  기존 테이블의 컬럼 변경은 안 된다.
- `usage_log`는 대화 턴만 기록하고(`log_usage("llm")`), 종류 구분·모델명이 없다. Anthropic 어댑터는
  `input_tokens`만 적어 캐시 토큰이 빠진다.
- D6이 문서마다 다르다 — plan.md는 sqlite-vec, architecture.md·aliveness.md는 Chroma. 벡터 저장을
  미뤘으므로 **"보류"로 통일**하는 것이 이 Phase의 문서 정리다.

## 4.1 사실 추출 — 구현된 형태 (3번, 2026.11.15)

코드: [navi/memory/facts.py](../../navi/memory/facts.py), 스키마는 `schema.sql`의 `fact`·`fact_cursor`.

**저장 형태.** 한 행 = 혼자 읽어도 뜻이 통하는 문장 하나. 사용자 단위다(페르소나와 무관).

| 컬럼 | 내용 |
| :-- | :-- |
| `kind` | `profile`(신상) / `preference`(선호) / `ongoing`(요즘 겪는 일) / `plan`(예정) |
| `text` | "사용자의 동생 이름은 민준이다." |
| `source_turn_id` | 이 사실이 나온 대화 턴 — 원문 확인과 연쇄 삭제의 축 |
| `status`, `superseded_by` | `active` / `superseded`. 대체된 사실은 지우지 않는다 |
| `expires_at` | 지나면 주입에서 빠진다(행은 남는다) |

- **문장인 이유:** 어떤 사실이 나올지 미리 정할 수 없어 키-값 구조를 못 쓴다. 문장은 그대로
  프롬프트에 들어가고 나중에 문장 단위로 임베딩된다.
- **프로필 문서 하나를 매번 다시 쓰는 방식은 기각.** 턴당 토큰은 가장 적지만, 대화 하나를 지울 때
  거기서 나온 내용만 골라 지울 수 없고(service.md G8 ④), 다시 쓸 때마다 내용이 조금씩 변하는 걸
  검증할 수 없다. 행이 원본이면 문서는 나중에 행에서 만들 수 있다 — 반대는 안 된다.
- **종류와 만료를 둔 이유:** "최근 순 N개"로만 고르면 오래됐지만 중요한 사실(가족 이름)이 밀린다.
  점수 대신 종류로 푼다 — `profile`은 항상 넣고 나머지에서 채운다(4번에서 구현). 만료는
  `plan`은 추출기가 준 끝 날짜, 없으면 30일. `ongoing`은 90일. `profile`·`preference`는 없음.
  **30·90은 감으로 잡은 값이다.**

**추출 시점.** 피드의 12시간 배치에 얹지 않고 따로 돈다 — 새 사용자 발화가 `min_new_user_turns`(4)개
쌓이면 tick에서 백그라운드로 1회. 커서(`fact_cursor`) 뒤의 대화만 본다. 한 번에 한 묶음
(`max_rows_per_batch` 40행)만 먹고, 뽑은 게 없어도 커서는 전진한다.

**추출기 출력 형식.** 콜백 추출과 같은 줄 태그다: `[fact:plan|src:T482|until:2026-12-01|replaces:F18] 문장`.
모델이 준 번호(`src`·`replaces`)는 그대로 믿지 않는다 — 이번 묶음에 없는 턴이면 마지막 사용자
발화로, 모르는 사실 번호면 무시한다.

**추출기 벤더.** `memory.facts.extractor.vendor`, 안 적으면 `feed.summarizer.vendor`를 따른다.
**echo면 추출이 꺼진다** — echo는 뽑는 게 없는데 커서만 전진해 그 대화를 되돌릴 수 없게 된다.
그래서 기본 config(요약기 echo)에서는 추출이 돌지 않는다. 켜려면 `config.local.yaml`에 벤더를 적는다.

**포트에 넣지 않은 것.** 추출기는 `MemoryStore`를 직접 쓴다(피드와 같다). 서버에서는 워커가
다른 저장소에 쓰게 되므로 지금 계약을 미리 고정하지 않았다. 읽는 쪽(`recall_relevant_facts`)만
4번에서 포트에 넣는다.

**실호출 확인 (2026.11.15, Haiku 4.5, 합성 대화 세 묶음 × 1회).** 임시 DB에 ①새 사실 ②앞 사실을
뒤집는 대화 ③잡담을 차례로 먹였다. 묶음당 입력 약 1,100~1,200토큰(규칙문이 대부분) / 출력 20~260토큰.

- **통과:** 줄 태그 형식 11줄 전부 파싱됨. 나비가 단정한 말("너 회 좋아하잖아")은 뽑지 않음(규칙 ④).
  "12월 5일"·"12월 20일"을 `until`로 계산. 이사·회사 이전·수면 세 건을 맞는 번호로 `replaces`.
  잡담 묶음은 0건.
- **규칙 ⑩은 샌다:** 잡담에 "뽑을 사실이 없습니다."라고 답했다. 줄 태그가 아니라 파서가 버린다 —
  줄 태그를 고른 이유가 이것이다.
- **★ 뒤집힌 사실이 "취소됐다"는 새 사실로 남는다.** "이사 계획을 취소했다"(plan), "회사는 부산 이전을
  접었다"(plan), "이제 잘 자고 있다"(ongoing)가 유효 사실로 들어가 30·90일 동안 주입 자리를 차지한다.
  옛 사실은 제대로 꺼졌지만, 없던 일이 된 것까지 기억할 값어치가 있는지는 별개다.
  **결정(2026.11.15): 그대로 둔다.** 새 문장 없이 끄기만 하는 태그(`[drop:F3]`)는 넣지 않는다 —
  ① "취소됐다"가 남아야 나비가 취소된 일을 다시 묻지 않는다 ② 끄기 태그는 모델이 번호를 잘못
  짚으면 대체 문장도 없이 사실이 조용히 사라지는 새 실패 경로다 ③ 남는 문장은 30·90일 뒤 저절로
  빠진다. 주입 자리가 실제로 모자라면 4번에서 상한을 정할 때 다시 본다.
- **한계:** 묶음당 1회라 응답 편차를 모른다. 긴 대화(40행 꽉 찬 묶음)·아는 사실이 수십 개일 때의
  중복 억제(규칙 ⑧)는 안 봤다.

## 4.2 조립에 사실 주입 — 구현된 형태 (4번, 2026.11.15)

**요청의 모양.** `LlmRequest`에 `context` 필드가 생겼다. 순서는 `system(카드) → context(사실) →
messages(최근 턴 + 트리거)` — 덜 변하는 것이 앞이다.

- **Anthropic:** 카드 뒤 별도 system 블록, 각자 캐시 경계. 사실이 바뀌어도 카드 경계는 맞는다.
- **Gemini:** `system_instruction` 뒤에 이어 붙인다(앞부분 일치로 캐시가 걸린다).
- 사실이 없으면 블록을 보내지 않는다.

**고르는 규칙** (`MemoryStore.recall_relevant_facts`). 유효한 사실 중 **신상(profile)을 먼저 다
넣고**, 남는 자리를 나머지의 최신 것으로 채운다. 상한은 `memory.facts.max_injected`(기본 50,
추정값). 순서는 신상 → 나머지, 각각 오래된 순 — 새 사실이 구간 끝에 붙어 앞쪽이 안 바뀐다.
`query`(이번 턴의 트리거)는 받기만 하고 안 쓴다(§1 조건 1).

**계획과 달라진 것.** §3은 "호출부가 미리 인출해 넘긴다"였는데, 조립이 포트에서 직접 읽게 했다.
최근 턴을 이미 그렇게 읽고 있어 사실만 빼면 인출이 두 곳으로 갈린다. 검색이 비동기가 되면
둘을 함께 옮긴다.

**인출 실패는 삼킨다.** 사실은 턴의 전제가 아니다 — 인출이 죽으면 경고만 남기고 사실 없이
답한다. (최근 턴 인출은 삼키지 않는다.)

**끄는 길 둘.** `memory.facts.enabled: false`(추출·주입 전부), `max_injected: 0`(추출은 두고 주입만).
추출 벤더가 echo여도 DB에 이미 있는 사실은 주입된다.

**머리말과 카드 공통 규칙의 충돌.** 카드 공통 규칙([persona/card.py](../../navi/persona/card.py))은
"이어지는 대화 기록만이 실제로 있었던 일이다"라고 말한다. 사실은 그 기록 밖에서 오므로 머리말이
"대화 기록에는 없어도 실제로 있었던 일"이라고 풀어 준다. system 쪽 문구는 건드리지 않았다
(사실이 없는 턴의 프롬프트가 안 바뀐다). 조립 로그를 보다 찾았다.

**기록하는 것.** 매 턴 조립 로그에 `사실 N건(M자)`(§1 조건 3). 토큰이 아니라 글자 수다.

**실호출 확인 (2026.11.15, Haiku 4.5, 나비 카드, 질문 4개 + 대조군 1개 × 1회).** 임시 DB에 사실
6건을 심고 **대화 기록은 비웠다** — 사실 블록이 유일한 출처다.

| 사용자 | 나비 | 판정 |
| :-- | :-- | :-- |
| 내 동생 이름 기억나? | 민준이지. 서울에서 대학 다니는 애. | 창 밖 사실을 답함 |
| 아 피곤해. 뭐 마실까? | 커피는 안 되지? 차나 물 마시는 게 어때? | 묻지 않은 사실을 맞게 씀 |
| 오늘 비 온다더라. | 어, 진짜? … 빨래 있으면 미리 들여놓는 게 나을 것 같은데. | 사실을 늘어놓지 않음 |
| 나 이사 준비 뭐부터 해야 하지? | 어? 이사? 부산 계획 취소했다고 하지 않았나? | 취소 사실로 되물음 |
| (주입 끔) 내 동생 이름 기억나? | 아직 안 들었어. | 대조군 — 답의 출처가 사실 블록임 |

- 카드 공통 규칙("대화 기록만이 실제")과의 충돌은 머리말로 풀렸다 — 기록이 비었는데도 사실을 썼다.
  머리말에 그 문장이 없을 때 어떤지는 재지 않았다.
- 넷째 줄은 §4.1의 결정("취소됐다"를 남긴다)이 실제로 쓰인 예다.
- **토큰:** 사실 6건 + 머리말이 약 300토큰(주입 켬 2,342 / 끔 2,038). 머리말을 빼면 건당 30토큰대라
  상한 50건이면 턴당 1,700토큰 안팎 — 카드(약 2,000)와 비슷한 크기다. 표본이 6건이라 거친 값이다.
- **한계:** 질문당 1회. 사실이 수십 건일 때(관련 없는 사실이 많을 때) 늘어놓는지, 선제 발화 턴에서
  어떻게 쓰이는지, 다른 언어 카드는 안 봤다.

## 4.3 최근 창 축소 — 구현된 형태 (5번, 2026.11.15)

**고정 길이를 줄이지 않고, 추출이 따라잡은 만큼만 줄어드는 창으로 바꿨다.**
`recent_turns: 20`을 그냥 8로 내리면 추출이 꺼진 설정(기본 config의 echo, 추출기가 안 도는
텍스트 CLI)에서는 기억이 나빠지기만 한다 — 빠진 대화가 사실에도 창에도 없다.

**규칙** (`MemoryPort.recall_working_window(user_id, min_rows, max_rows)`). 추출 커서 뒤의 행이
n개면 창은 `max(min_rows, n)`행이고 `max_rows`를 넘지 않는다.

- 아직 사실로 옮기지 않은 대화는 전부 창에 남는다(상한 안에서).
- 추출이 돌면 창이 하한으로 줄고, 대화가 쌓이면 다시 늘어난다.
- 커서가 안 움직이면 늘 상한이다 — 예전 거동과 같다.
- 사실 주입을 끄면(`enabled: false`·`max_injected: 0`) 조립이 예전의 고정 창을 쓴다.
  창을 줄여도 되는 근거가 "사실이 대신한다"뿐이기 때문이다.

설정은 `memory.recent_turns`(상한 20, 그대로)와 `memory.recent_turns_min`(하한 8, 신규).
하한 8은 추출 한 묶음(사용자 발화 4개 ≈ 8행)에 맞춘 추정값이다.

**전후 비교 (2026.11.15, Haiku 4.5, 나비 카드, 질문 4개 × 1회).** 합성 대화 40행, 앞 10행에
사실 넷을 심고 뒤 30행은 잡담. 같은 DB에서 조립만 바꿨다. 사실은 실제 추출기가 뽑았다(1회, 5건).

| | 최근 대화 | 사실 | 정답 | 턴당 입력 토큰 |
| :-- | :-- | :-- | :-- | :-- |
| 이전 (사실 없음 + 고정 창) | 20행 | 0건 | 0/4 | 2,392 |
| 이후 (사실 주입 + 줄어든 창) | 8행 | 5건 | 4/4 | 2,506 |

- **회상은 얻었고 토큰은 줄지 않았다(+5%).** §4의 검증 기준 "토큰이 줄었는가"는 충족하지 못했다.
  창 12행을 덜어 낸 것보다 사실 5건 + 머리말이 더 크다. 사실이 늘수록 차이는 벌어진다.
  이 Phase의 성과는 토큰 절감이 아니라 **같은 비용 근처에서 창 밖을 기억하는 것**이다.
- 잡담 행이 짧아(행당 십여 토큰) 창 축소의 효과가 작게 나온 면이 있다. 실제 대화는 더 길 것이다 — 미측정.
- "이전"은 F1에서 재려던 기준선과 같은 조립이다(사실 끔 = 2번 직전과 동일한 요청). 미뤄 둔
  기준선 측정을 이 표가 대신한다. 거리별(5/15/25/…) 곡선은 재지 않았다.
- **한계:** 질문당 1회, 대화 1종, 하한 8의 적정성(말의 흐름이 끊기는지)은 안 봤다.

## 5. 기준선 측정

**① 턴당 입력 토큰**

- 실제 `Conductor.build_request`로 요청을 조립하고, 벤더의 토큰 카운트 API로 센다.
  `usage_log`는 보조다(캐시 토큰이 빠져 있다).
- 대화 길이별로 잰다: 0행 / 20행(창이 가득 참) / 그 이상(창이 잘림).
- 카드·규칙·최근 턴이 각각 몇 토큰인지 나눠 적는다.

**② 회상 테스트**

- 합성 한국어 대화 약 200행에 사실 20~30개를 심는다(예: "동생 이름은 ○○", "다음 달 이사").
- 사실을 심은 지점에서 질문까지의 거리: 5 / 15 / 25 / 50 / 100 / 200행.
  20행 창 안(5·15)은 맞히고 밖은 틀리는 것이 예상 기준선이다.
- 채점은 정답 키워드 포함 여부. 질문당 3회 돌린다(응답 편차).
- 실제 LLM 호출이 든다 — 질문 수 × 거리 6 × 3회. 비용은 실행 전에 계산해 확인받는다.

**③ 함께 기록할 것:** 사용자별 사실 수, 턴당 주입 토큰(§1의 조건 3).

## 6. 미정

- 사실 상한 `k`. 추정으로는 50개 안팎이 현실적이다 — 200개를 전부 넣으면 턴당 비용이 약 3배가 된다
  (미측정, service.md §6.0.1의 추정과 같은 계산).
- 사실의 갱신·모순 처리("이사 갈 거야" → "이사 취소됐어"): 대체됨 표시 vs 덮어쓰기.
- 추출 주기와 한 번에 보는 턴 수(지금 콜백 추출은 `recent_turns_for_extract: 30`).
- 사용자가 사실을 보고 지우는 경로(aliveness.md §3.4, service.md G8 ④).
- 페르소나별 대화 분리(service.md §16)를 로컬 스키마에도 넣을지 — 서버 스키마에는 들어간다.
